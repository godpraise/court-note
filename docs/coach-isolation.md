# 코치별 데이터 분리

구현·검증일: 2026-11-13. 현재 로컬 수정본이며 서비스 배포 전이다.

## 적용 범위

- 로그인 사용자의 Firebase Auth UID를 데이터 경로에 사용한다.
- `venues`, `members`, `lessons`, `passes`, `journals`, `skills`, `progress`를 `coaches/{uid}` 아래에 저장한다.
- 클라이언트가 임의의 UID를 입력해 다른 코치의 경로에 요청해도 Firestore 규칙이 거부한다.
- 이메일 인증과 `admins/{로그인 이메일}` 등록을 모두 요구한다. 접근 목록은 콘솔·Admin SDK로만 관리한다.
- `/api/clean-note`도 동일한 등록 코치 여부를 서버에서 확인하며, 확인 실패 시 AI API를 호출하지 않는다.
- 로그아웃·구독 오류 시 캐시와 화면을 초기화하고 모든 구독을 해제한다. 늦게 도착한 이전 세션 콜백은 무시한다.
- 같은 문서에서 다른 UID로 바뀌면 페이지를 다시 로드하여 이전 UI의 비동기 작업도 새 계정으로 이어지지 않게 한다.

## 기존 데이터

사용자는 기존 공통 데이터가 테스트 자료이며 새 코치는 빈 상태로 시작해도 된다고 확인했다. 따라서 기존 루트 컬렉션을 삭제하거나 새 코치에게 복사하지 않는다. 새 보안 규칙은 이 공통 자료에 대한 클라이언트 접근을 거부한다. 데이터 자체는 기존 Firebase 프로젝트에 남는다.

두 이메일은 서로 다른 UID라면 서로 다른 코치로 취급한다. 같은 코치가 여러 기기에서 같은 계정으로 로그인하면 같은 데이터를 사용한다. 향후 여러 계정이 같은 코치 조직을 공유해야 한다면 별도의 멤버십 모델을 설계해야 한다.

## 검증

권장 런타임은 Node.js 22 이상과 Java 21 이상이다. 개발 패키지를 포함해 설치한다.

```sh
npm ci
npm test
npm run test:rules
```

`test:rules`는 `demo-court-note-isolation`이라는 로컬 전용 프로젝트와 `127.0.0.1:8787`을 사용한다. 테스트 코드는 에뮬레이터 주소가 다르면 실행을 거부한다. 실제 Firebase 계정·운영 데이터·Anthropic API를 사용하지 않는다.

- 단위 테스트 11개: UID 경로, 잘못된 경로, 구독 정리, 늦은 응답, 계정 전환, 권한 오류, AI API의 인증·등록·입력 검증.
- Firestore 에뮬레이터 테스트 7개: 본인 데이터 CRUD와 목록 조회, 다른 코치 7개 컬렉션의 접근 거부, 미등록·미인증·비로그인 거부, 접근 목록 변경 차단, 공통 데이터 접근 차단, 권한 회수, 새 코치의 빈 상태.
- 별도 브라우저 확인: 모의 Firebase SDK로 실제 앱 화면을 열어 코치 A/B 회원 표시, 로그아웃 후 화면 초기화, 늦은 응답 무시, 계정 변경, 미등록·이메일 미인증 거부를 확인했다.

에뮬레이터 테스트는 규칙 엔진을 실행한 로컬 검증이며 실제 배포된 규칙 검증이 아니다. 브라우저 확인도 모의 SDK를 사용했다. 실제 이메일 링크·서버 환경변수·AI 응답·기기 간 동작은 배포 후 확인이 필요하다.

## 실제 서비스에 반영할 때

아직 아래 배포 명령은 실행하지 않았다. Firebase와 Vercel의 프로젝트를 확인하고 반영해야 한다.

1. Firestore에 필요한 코치의 `admins/{이메일}` 문서가 있는지 확인한다. 이메일 링크 로그인을 사용하며 계정의 이메일 인증이 필요하다.
2. 현재 프로젝트의 기존 데이터·규칙을 보관하고, 준비한 `firestore.rules`를 대상 Firebase 프로젝트에 배포한다. 새 규칙 적용 시 구버전 앱은 공통 컬렉션에 접근할 수 없게 된다.
3. `index.html`, `coach-session.js`, `lesson-completion.js`, `sw.js`, `/api/clean-note.js`와 기존 PWA 자산을 Vercel에 함께 배포한다. 서버의 기존 환경변수는 유지한다.
4. 새로고침하여 서비스 워커를 갱신하고, 별도 테스트 코치 계정 두 개로 서로의 회원·레슨이 보이지 않는지 확인한다.
5. 허용 목록에 없는 계정과 다른 코치의 경로에 대한 직접 요청도 거부되는지 확인한다. AI 메모는 허용된 계정으로만 요청한다.

규칙을 먼저 반영하면 구버전 화면은 일시적으로 데이터를 읽지 못한다. 구버전의 공유 허용 규칙과 새 클라이언트를 장기간 혼용하지 않는다. 문제가 생기면 검증된 분리 버전을 고치거나 일시적으로 접근을 막고, 공유 허용 규칙으로 무심코 되돌려 코치 간 접근을 열지 않는다.

- 동일 레슨 반복·동시 완료는 2026-11-16 후속 트랜잭션에서 로컬 검증했다. 완료 후 편집·취소 시 역정산, 기존 불일치 데이터 복구는 별도 과제다. [후속 검증](lesson-completion.md)을 참고한다.
- 실제 운영 규칙·이메일 링크·서버 환경변수·AI 응답·다중 기기 확인.
- 기존 `firebase-admin` 12 계열 운영 의존성의 감사 결과에 남아 있는 중간 등급 항목은 별도 업데이트 검토 대상이다. 이번 분리 검증을 전체 의존성 보안 검증으로 해석하지 않는다.
